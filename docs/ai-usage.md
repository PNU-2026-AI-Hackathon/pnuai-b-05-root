## 2. 활용 범위

**개발 과정**: Claude Code를 기획부터 백엔드 API, 프론트엔드 화면, 테스트 코드 작성까지 전 단계에 걸쳐 활용했습니다. 특히 해커톤 후반부에는 실기기 검증 중 발견된 버그 수정과 기존 화면 개선(예: RAG 챗봇 응답 품질 개선, 재배자 일지 삭제 기능, 묘목 완성 신고 실측 데이터화, 환경 이상 감지 시각화, 탈퇴 계정 처리 등) 다수를 이 방식으로 진행했습니다.

**서비스 내 AI**: Gemini API는 재배자가 올린 사진을 입양자용 감성 일러스트로 변환하는 데 사용되며, 같은 모델이 RAG 챗봇의 답변 생성과 센서 이상 상황의 자연어 진단 문구 생성에도 쓰입니다. YOLOv8은 API 호출이 아니라 직접 모델을 만든 사례로, 무화과 잎 healthy/infected 이미지로 구성된 Fig Leaves Dataset(총 2,321장)을 Google Colab(Tesla T4 GPU) 환경에서 YOLOv8n-cls 사전학습 가중치 기반으로 파인튜닝했습니다. 클래스별 80:20으로 train/val을 층화 분할(train 1,857장/val 464장)하고, 최대 40 epoch·조기종료(patience 10) 조건으로 38 epoch에서 학습을 마쳐 val top1 정확도 97%를 달성했습니다. Prophet은 센서 시계열 데이터 기반 이상 감지를 담당하며, 그 결과는 Gemini가 사람이 읽기 쉬운 문장으로 변환합니다.

## 3. AI 생성 코드의 검증·수정 방식

이 프로젝트는 **"계획 → 실제 코드 대조 확인 → 승인 → 구현 → 완료 보고 재검증 → 커밋"** 순서를 팀의 기본 작업 흐름으로 삼았습니다.

1. **계획 단계 검증**: Claude Code가 작업에 착수하기 전, 변경이 필요한 이유와 구체적인 구현 계획을 먼저 제시하도록 했습니다. 이 계획서는 곧바로 승인하지 않고, 실제 저장소 코드를 직접 열어 계획서에 인용된 파일 경로·줄 번호·기존 패턴(예: 기존에 동일한 목적으로 쓰이던 클래스나 함수)이 실제로 존재하는지 하나하나 대조했습니다. 이 과정에서 존재하지 않는 근거를 든 계획이나 실제 코드와 다른 전제를 세운 계획을 여러 차례 걸러냈습니다.
2. **설계 결정의 명시적 확인**: 완료 처리 기준(예: 묘목 완성 신고 시 키 30cm 미달을 차단할지), 데이터 보존 정책(예: 회원탈퇴 시 소프트 삭제 유지) 등 되돌리기 어렵거나 사용자 경험에 영향을 주는 결정은 Claude Code가 스스로 판단하지 않고 사람에게 먼저 질문하도록 규칙을 두었습니다.
3. **구현 후 검증**: 매 변경마다 `flutter analyze` / `python manage.py check`, 관련 단위·위젯 테스트, 그리고 필요한 경우 `flutter build web` + Playwright 헤드리스 브라우저로 실제 화면을 스크린샷 검증했습니다. 에뮬레이터/실기기 구동은 이 개발 환경(Windows, Winsock 소켓 문제)에서 불안정해 기본적으로 제외하고, 꼭 필요한 경우에만 사전 동의를 받고 진행했습니다.
4. **완료 보고 재검증**: 구현이 끝난 뒤에도 변경된 파일과 실제 diff, 테스트 통과 수치를 다시 코드로 확인한 뒤에만 커밋·PR 병합을 승인했습니다. 이 과정에서 한 번은 커밋 스테이징 실수로 백엔드 변경분이 누락된 채 첫 커밋이 올라간 것을 병합 전에 발견해 추가 커밋으로 바로잡았습니다.
5. **배포 반영 확인**: `requirements.txt` 변경처럼 배포 환경에만 영향을 주는 변경(예: RAG 챗봇이 배포 환경에서만 `chromadb` 패키지 누락으로 항상 폴백 응답을 내던 문제)은 실제 배포 로그와 서비스 엔드포인트에 대한 curl 요청으로 배포 후 상태까지 재확인했습니다.

이러한 흐름을 통해 AI가 생성한 코드를 무조건 신뢰하지 않고, 매 단계에서 실제 저장소 상태와 대조하여 근거 없는 주장이나 회귀를 사전에 차단하는 것을 원칙으로 삼았습니다.
